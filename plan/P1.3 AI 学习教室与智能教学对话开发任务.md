## 四、AI 老师核心行为

这是本阶段最重要的部分。

AI 不应该只是等待用户提问。

用户进入一个尚未开始学习的知识点时，AI 应该主动发起教学。

### 1. 主动讲解

AI 必须根据当前课程和知识点内容，主动开始教学。

讲解要求：

- 用通俗易懂的语言解释概念。
- 假设用户是初学者。
- 解释为什么需要这个知识点。
- 说明它解决什么问题。
- 使用生活化例子帮助理解。
- 给出必要的技术术语解释。
- 讲解不能只是一段简短摘要。
- 不要一上来就要求用户自己写代码。

### 2. 案例演示

讲解知识点后，AI 应该能够展示一个完整的小案例。

要求：

- 案例能够对应当前知识点。
- 先展示完整代码。
- 再逐段解释代码。
- 解释每个重要语句的作用。
- 展示运行结果或预期输出。
- 说明常见错误。
- 说明实际项目中的应用场景。

本阶段只负责展示和解释代码，不要求网页实际执行代码。

### 3. 教学互动

提供以下快捷操作：

- 再讲一遍
- 换个例子
- 慢一点讲
- 举实际项目例子
- 解释这段代码
- 我有一个问题

用户点击后，AI 必须结合当前知识点和已有对话继续教学，而不是返回固定模板。

### 4. 自由提问

用户可以随时提出自己的问题。

AI 应当：
- 结合当前课程教材。
- 结合当前知识点。
- 结合此前对话。
- 优先解释当前知识范围内的问题。
- 不理解时主动换一种解释方式。
- 不要无视用户的问题继续机械讲课。

### 5. 教学行为约束

必须遵守：

1. 老师先教，学生后练。
2. 不要一开始就要求用户写代码。
3. 不要连续抛出多个问题。
4. 不要把整章内容一次性全部输出。
5. 每次围绕一个知识点展开。
6. 用户表示不理解时，换例子或拆小步骤。
7. 不要虚构教材中不存在的内容。
8. 教材没有提供的信息，可以补充通用知识，但必须区分教材内容与补充解释。
9. 不要在本阶段擅自判断用户已经掌握知识点。
10. 不要擅自跳过用户选择的知识点。

## 五、AI 对话技术实现

### 1. 使用现有模型配置

复用 P0 已实现的模型配置功能。

要求：
- 使用用户实际配置的 API Base URL。
- 使用用户实际配置的 API Key。
- 使用用户选择的模型。
- 不允许硬编码模型名称。
- API Key 只能由后端读取和使用。
- 前端不得直接携带密钥请求第三方模型接口。

### 2. 流式输出

实现真实 AI 流式响应。

要求：
- 后端支持 SSE 或适合现有架构的流式接口。
- 前端逐步显示 AI 输出。
- 支持 Markdown 渲染。
- 支持代码块高亮。
- 支持数学公式。
- 支持 Mermaid 图表（如项目现有依赖适合）。
- 处理网络中断和 API 错误。
- 显示正在生成状态。

不能使用定时器模拟流式输出，必须使用真实模型返回的数据流。

### 3. 停止生成

支持用户中断 AI 生成。

要求：
- 前端停止当前请求。
- 后端尽可能取消正在进行的模型请求。
- 停止后保留已经生成的内容。
- 不允许停止后继续追加旧请求内容。

### 4. 对话上下文

每次请求需要正确携带：

- 当前课程信息。
- 当前章节信息。
- 当前知识点内容。
- 当前会话历史。
- 用户当前问题。

需要控制上下文长度，避免无意义地发送整本教材。

长对话应有合理的历史消息裁剪策略。

### 5. 对话持久化

设计并实现对话数据模型。

至少考虑：

LearningSession：
- id
- course_id
- knowledge_point_id
- created_at
- updated_at

ChatMessage：
- id
- session_id
- role
- content
- created_at

具体字段以现有数据库规范为准。

要求：
- 每个知识点能够对应学习会话。
- 消息能够按时间顺序恢复。
- 刷新页面不丢失对话。
- 重新打开课程能够恢复历史。
- 不同课程之间的会话不能混淆。

## 六、AI 教学提示词设计

不要将所有教学逻辑写死在前端。

在后端独立维护 AI 教学提示词模块。

将以下职责区分：

1. 系统角色：定义 AI 老师的身份和教学原则。
2. 课程上下文：提供当前课程和教材内容。
3. 知识点上下文：提供当前教学目标。
4. 对话历史：提供之前的师生交流。
5. 用户请求：当前需要回答的问题。

要求提示词可维护、可扩展。

本阶段先实现主动讲解、案例演示和自由提问能力。

不要把 P1.4 的完整状态机提前塞进提示词。
